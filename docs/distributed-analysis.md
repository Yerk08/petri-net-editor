# Архитектура сервера распределенного анализа сетей Петри

> **Статус:** Проектирование

Документ описывает целевую архитектуру распределенного вычислительного кластера для тяжелого математического анализа сетей Петри (построение графов достижимости, поиск тупиков, проверка живости и ограниченности).

---

## 1. Базовые архитектурные принципы

1. **Инкапсуляция логики на сервере:** Вычислительные узлы (воркеры) не хранят алгоритмы анализа. Сервер декомпозирует задачу и передает воркеру готовый к исполнению Python-скрипт со вшитыми данными подзадачи.
2. **Изоляция вычислений:** Выполнение полученного кода на стороне воркера происходит в изолированной среде (WASM в браузере или изолированный Docker-контейнер без доступа к сети и диску) с очисткой памяти после завершения или отмены.
3. **Ускорение расчетов:** Внутри воркеров используется связка Python + NumPy / Numba (JIT-компиляция матричных операций для нативных воркеров и пустая обертка декоратора `@njit` для браузерного WASM).
4. **Квантование и отмена:** Задачи дробятся на независимые мелкие подзадачи (чанки), что обеспечивает балансировку нагрузки между клиентами и мгновенную отмену расчетов по команде через канал heartbeat.
5. **Серверный Byzantine Fault Tolerance:** Каждая подзадача дублируется на $N$ независимых воркеров. Решение принимается только при достижении кворума идентичных результатов; узлы с систематическими расхождениями блокируются.

---

## 2. Компоненты системы

### 2.1. Сервер-планировщик (Master)
Реализуется на **[Go](https://go.dev)** (веб-фреймворк Fiber или Echo) со встроенным скриптовым движком **Lua** (`gopher-lua`) и хранилищем состояния SQLite для автономного режима / Redis для кластерного.

* **Управление кластером:** Регистрация воркеров, контроль живучести по TTL (`heartbeat`), управление очередью чанков, BFT-сверка результатов и ведение репутации узлов.
* **Модульная система алгоритмов с горячей перезагрузкой (Hot Reload):**
  Сервер отслеживает директорию алгоритмов через `fsnotify`. Каждый алгоритм представляет собой изолированный пакет из трех файлов:
  * `meta.json` — метаданные алгоритма и схема параметров формы для фронтенда.
  * `orchestrator.lua` — единый скрипт с функциями `split(params)` (нарезка задачи на чанки) и `merge(results)` (агрегация проверенных ответов в краткий итог и HTML-отчет). Исполняется в изолированной ВМ без доступа к модулям `os` и `io`.
  * `worker_algo.py` — шаблон математического алгоритма для воркеров.
* **Версионирование при обновлении:** При изменении файлов алгоритма сервер валидирует их, прекомпилирует байт-код Lua и атомарно регистрирует новую версию для входящих задач. Активные задачи продолжают выполнение на версии, актуальной на момент их создания.

### 2.2. Вычислительные узлы (Workers)
Поддерживаются два типа узлов, работающих по единому протоколу:

1. **Браузерный WASM-воркер:** Фоновый поток Web Worker на базе Pyodide (WebAssembly) + Numba для подключения пользователей в один клик без установки дополнительного ПО.
2. **Выделенный Docker-воркер:** Изолированный Docker-контейнер с нативным Python и Numba, поддерживающий многопоточную обработку пачек чанков и кеширование скомпилированных функций в оперативной памяти.

## 3. Жизненный цикл задачи

1. **Инициализация:** Клиент отправляет параметры сети и тип анализа. Сервер фиксирует текущую версию алгоритма и присваивает задаче идентификатор.
2. **Декомпозиция (`split`):** Сервер вызывает `orchestrator.lua:split(params)` и помещает сформированные подзадачи в очередь с учетом коэффициента BFT-дублирования.
3. **Распределение и расчет:** Свободные воркеры запрашивают пачки чанков, получают сгенерированные `.py`-скрипты (шаблон `worker_algo.py` + данные чанка) и исполняют их с соблюдением жесткого лимита времени и регулярным опросом `heartbeat`.
4. **BFT-верификация:** Сервер сравнивает возвращаемые воркерами результаты. При сборе кворума чанк считается решенным, а остальным воркерам, считающим этот же чанк, отправляется команда прерывания. Технические сбои песочницы (OOM, таймаут) приводят к переназначению чанка без штрафа к репутации узла.
5. **Агрегация (`merge`):** После верификации всех чанков сервер передает массив результатов в `orchestrator.lua:merge(results)`, сохраняет краткий итог и итоговый HTML-отчет, переводя задачу в статус готовности. При отмене задачи клиентом оставшиеся чанки удаляются из очереди, а активным воркерам рассылается команда прерывания.

## 4. План реализации

- [ ] **Ядро планировщика (Go):** HTTP API, менеджер сессий воркеров (TTL), потокобезопасная очередь чанков с поддержкой массовой отмены.
- [ ] **Плагин-менеджер (Go + `gopher-lua` + `fsnotify`):** Загрузка, песочница, прекомпиляция и версионирование пакетов алгоритмов (`meta.json`, `orchestrator.lua`, `worker_algo.py`).
- [ ] **BFT-контроллер:** Логика репликации чанков, подсчет кворума по результатам, обработка таймаутов и система банов.
- [ ] **Среда воркера:** Асинхронный цикл опроса/heartbeat и исполнители для Docker (Python + Numba) и браузера (Pyodide WASM).
- [ ] **Пакеты алгоритмов:** Реализация `split`, `merge` и `worker_algo.py` для базовых задач анализа сетей Петри.
- [ ] **Автономная сборка:** Единый контейнер/бинарник («сервер + локальный воркер») для офлайн-работы без доступа к интернету внутри браузера.
