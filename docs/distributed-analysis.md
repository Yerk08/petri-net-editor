# Архитектура сервера распределенного анализа сетей Петри

> **Статус:** Реализовано

## 1. Базовые архитектурные принципы

1. **Инкапсуляция логики на сервере:** Вычислительные узлы (воркеры) не хранят алгоритмы анализа. Сервер-координатор декомпозирует задачу и выдает воркеру готовый Python-скрипт и JSON-данные конкретного чанка.
2. **Изоляция вычислений:** Выполнение полученного кода на стороне воркера происходит в изолированной среде (WASM в браузере или изолированный Docker-контейнер). На стороне мастера оркестрация алгоритмов выполняется в изолированной песочнице Lua без доступа к модулям `os` и `io`.
3. **Ускорение расчетов:** Внутри воркеров используется связка Python + NumPy / Numba (JIT-компиляция `@njit` для нативных воркеров и пустая обертка декоратора для браузерного WASM).
4. **Корутинная оркестрация (MapReduce в Lua):** Управление жизненным циклом задачи реализовано на базе Lua-корутин (`coroutine.yield`). Алгоритм может запускать одну или несколько последовательных волн вычислений, динамически формируя новые чанки на основе промежуточных результатов.
5. **Отказоустойчивость и репутация (BFT / Strikes):**
   * Сервер гарантирует, что разные реплики чанков с одинаковым `tag` в рамках одной задачи не попадут на один и тот же вычислительный узел.
   * Оркестратор алгоритма имеет доступ к API репутации (`ctx.strike_worker`): при расхождении результатов кворума воркер получает страйк и автоматически блокируется (`Banned`) при достижении лимита.
   * Технические сбои и потеря связи с воркером по таймауту (`WORKER_LOST`) обрабатываются внутри Lua-сценария через повторную постановку чанков в очередь без штрафа к репутации узла.

## 2. Компоненты системы

### 2.1. Сервер-планировщик (Master)
Реализован на Go (стандартная библиотека `net/http` с поддержкой CORS и маршрутизацией Go 1.22+) со встроенным скриптовым движком **Lua** (`gopher-lua`) и хранением активного состояния в оперативной памяти с автоматической очисткой завершенных задач по TTL (`MaxTimeRememberMinutes`).

* **Управление кластером (`cluster.go`):** Регистрация воркеров, фоновый мониторинг живучести по `LeaseTimeoutMs` (`reapDeadWorkers`), управление потокобезопасной очередью чанков и рассылка команд прерывания (`AbortQueue`) через канал `heartbeat`.
* **Модульная система алгоритмов с горячей перезагрузкой (`plugin_manager.go`):**
  Сервер в реальном времени отслеживает директорию алгоритмов через `fsnotify` (поддерживается добавление, обновление и удаление пакетов без перезапуска мастера). Каждый алгоритм представляет собой папку с тремя файлами:
  * `meta.json` — идентификатор, отображаемое имя, схема входных параметров для динамической генерации формы на фронтенде (`color_filter`, `marking_filter`, `number` и др.) и лимиты выполнения.
  * `orchestrator.lua` — скрипт с единой точкой входа `main(ctx)`, который валидирует параметры, нарезает задачу на чанки, вызывает `coroutine.yield({ chunks = ... })`, собирает результаты и формирует `short_result` и `html_report`.
  * `worker_algo.py` — математическое ядро алгоритма с функцией `run_chunk(raw_data: str) -> str`.
* **Версионирование:** При изменении файлов пакета сервер проверяет синтаксис Lua в изолированной ВМ и атомарно регистрирует новую версию пакета для входящих задач. Уже запущенные задачи продолжают работу со своей версией пакета.

### 2.2. Вычислительные узлы (Workers)
Поддерживаются два типа узлов, работающих по единому HTTP-протоколу (`/worker/register`, `/worker/pull`, `/worker/heartbeat`, `/worker/submit`, `/worker/unregister`):

1. **Браузерный WASM-воркер:** Фоновый поток Web Worker на базе Pyodide (WebAssembly) для подключения вычислительных мощностей прямо из браузера пользователя.
2. **Выделенный Docker-воркер:** Изолированный контейнер с нативным Python и Numba, поддерживающий многопоточную обработку пачек чанков (`freeSlots`) и кеширование JIT-скомпилированных функций.

## 3. Жизненный цикл задачи

1. **Инициализация:** Клиент запрашивает список алгоритмов (`/api/v1/get_types`) и схему параметров (`/api/v1/get_schema`), после чего отправляет задачу через `POST /api/v1/submit_task`. Сервер создает объект `Task` и запускает его Lua-корутину (`stepTask`).
2. **Декомпозиция (Map):** Функция `main(ctx)` в `orchestrator.lua` разбивает задачу на независимые батчи и приостанавливает выполнение через `coroutine.yield({ chunks = batch })`. Сервер помещает чанки в общую очередь.
3. **Распределение и расчет:** Свободные воркеры запрашивают пачки задач через `POST /worker/pull`, исполняют `run_chunk` и периодически отправляют `POST /worker/heartbeat` для продления аренды и проверки наличия команд `abort` или `ban`.
4. **Сбор волны и повторные попытки:** По мере выполнения воркеры отправляют ответы в `POST /worker/submit`. Как только все чанки текущей волны завершены (успешно или с ошибкой), мастер возобновляет Lua-корутину (`Resume`), передавая массив `ChunkResult`. При необходимости Lua-скрипт может перезапустить упавшие чанки (до `max_retries`) или запустить следующую стадию расчетов.
5. **Агрегация (Reduce) и завершение:** Собрав все данные, `orchestrator.lua` формирует краткую сводку и полный HTML-отчет (включая SVG-графики, таблицы и логи) и возвращает `{ short_result, html_report }`. Задача переходит в статус `ready`, а клиент забирает результат через `/api/v1/check_task` и `/api/v1/get_full_result`. При отмене задачи (`POST /api/v1/cancel_task`) активным воркерам рассылается команда прерывания.

## 4. Реализованные подсистемы и API

* **Ядро планировщика (`main.go`, `cluster.go`):** Потокобезопасная очередь чанков с защитой от дублирования BFT-тегов на одном узле, мониторинг ресурсов кластера (`/api/v1/cluster_status`), пакетная проверка статусов (`/api/v1/check_tasks`) и механизм принудительной отмены задач.
* **Мост Go ↔ Lua (`lua_bridge.go`):** Песочница `gopher-lua`, двусторонняя рекурсивная конвертация структур данных, встроенные хелперы `ctx.json_encode`, `ctx.json_decode` и `ctx.strike_worker`.
* **Плагин-менеджер (`plugin_manager.go`):** Динамическая загрузка, валидация, версионирование и горячая перезагрузка пакетов через `fsnotify`.
* **Пакеты алгоритмов:** Реализованы пакеты анализа сетей Петри (включая `monte_carlo_sim` с Numba-ускорением на воркере и генерацией интерактивного HTML/SVG-отчета в Lua).

## 5. Дальнейшее развитие (Roadmap)

- [ ] **Полноценная поддержка WebGPU:** Интеграция вычислительных шейдеров (WGSL) в браузерный и нативный контуры выполнения воркеров. Это позволит перенести массивно-параллельные матричные операции и тысячи независимых прогонов стохастических симуляций (Монте-Карло) с CPU на видеокарту клиента без необходимости установки CUDA или драйверов.
- [ ] **Маршрутизация с учетом аппаратных возможностей (GPU-aware scheduling):** Расширение телеметрии воркеров при регистрации (`/worker/register`) флагом поддержки WebGPU и передача мастером крупных батчей на GPU-совместимые узлы.
