# 💡 Концепт: Сервер распределенного анализа сетей Петри

> **Статус:** Проектирование  
> На текущий момент в репозитории доступен только прототип клиентского API в виде `mock.py`.

Этот документ описывает целевую архитектуру распределенной вычислительной системы, которую предстоит реализовать для тяжелого анализа сетей Петри (построение графов достижимости, поиск тупиков, проверка живости и ограниченности).

---

## 🎯 Основная идея

Тяжелый математический анализ больших сетей Петри требует значительных вычислительных ресурсов. Идея заключается в том, чтобы создать **распределенный кластер**, к которому сможет подключиться любой желающий (волонтер или выделенный сервер) и отдать часть мощностей своего ПК под расчеты.

Чтобы система была безопасной, быстрой и защищенной от подмены данных, в основу закладываются следующие принципы:

1. **Алгоритмы знает только сервер:** Воркеры (подключенные компы) не хранят у себя логику анализа. Сервер сам нарезает задачу на куски и присылает воркеру данные **вместе с кодом**, который нужно выполнить прямо сейчас.
2. **Полная изоляция через WASM:** Код на стороне воркера должен крутиться внутри Node.js в песочнице WebAssembly (WASM). Это защищает комп воркера от чужого кода, а серверу гарантирует, что алгоритм отработает в чистой среде и не осядет на диске.
3. **Скорость через Numba:** Внутри WASM-окружения запускается Python с библиотекой `Numba` (JIT-компиляция), чтобы матричные вычисления над сетями Петри работали максимально быстро.
4. **Мелкие кванты времени:** Задачи дробятся на совсем небольшие подзадачи. Это позволяет кластеру «жонглировать» десятками клиентских запросов одновременно и мгновенно отменять расчеты, если пользователь нажал «Отмена».
5. **Серверный BFT (Byzantine Fault Tolerance):** Так как воркерам нельзя доверять (кто-то может специально слать мусор, а у кого-то просто сбойнет железо), проверкой занимается строго сервер. Он скармливает одну и ту же подзадачу сразу нескольким разным компам и сверяет их ответы.

---

## 🏗 Как это должно быть устроено

### 1. Сервер-планировщик (Master)
Главный координатор (на базе **Node.js** или **Flask** + БД для трекинга). Сам он ничего тяжелого не считает, а только управляет процессами:

* **Общение с фронтендом:** Принимает задачи от пользователей редактора, отдает статусы и итоговые отчеты (интерфейс уже заложен в `mock.py`).
* **Учет воркеров:** Когда новый комп хочет помогать с расчетами, он стучится на сервер. Сервер выдает ему уникальный `workerId`, записывает в базу и следит, жив ли он.
* **Приватное хранилище модулей:** На сервере для каждого вида анализа лежат три Python-скрипта:
  * `splitter` — умеет брать большую задачу и резать ее на кучу независимых мелких подзадач.
  * `algorithm` — сам математический алгоритм (именно этот код отправляется воркерам).
  * `merger` — умеет склеивать готовые куски ответов от воркеров в единый финальный результат.

### 2. Вычислительные узлы (Workers)
Клиентская часть для тех, кто предоставляет мощности (в идеале упакованная в **Docker-образ** или запускаемая как простой скрипт на **Node.js**):

* Подключается к серверу, получает свой `workerId` и начинает постоянно опрашивать сервер на наличие работы.
* Получив пакет (`подзадача` + `код algorithm`), поднимает в памяти **WASM-контейнер**.
* Внутри WASM запускается связка **Python + Numba**, прогоняет `algorithm` на полученных данных и возвращает результат.
* После выполнения память WASM-контейнера очищается — на компьютере воркера не остается ни данных сети, ни кода алгоритма.

## 🔄 Как должен проходить жизненный цикл задачи

1. **Запрос клиента:** Пользователь в редакторе нажимает «Анализировать». Фронтенд отправляет задачу и параметры на `/submit_task`, сервер отвечает `taskId` (работа пошла).
2. **Нарезка (Splitter):** Сервер берет задачу и прогоняет ее через свой внутренний `splitter`. На выходе получается очередь из сотен маленьких подзадач.
3. **Раздача с кодом:** Свободные компы (воркеры) забирают подзадачи из очереди. Вместе с куском данных сервер отдает им исходник `algorithm`.
4. **Быстрый счет в песочнице:** Воркер за доли секунды (или пару секунд) прокручивает код в `Node.js -> WASM -> Python (Numba)` и шлет ответ обратно.
5. **BFT-проверка на сервере:**
   * Сервер не верит первому же ответу. Одну и ту же подзадачу он параллельно выдает, например, **3 или 5 разным воркерам**.
   * Когда ответы приходят, сервер сравнивает их между собой. Если большинство (кворум) прислали одинаковый результат — подзадача считается решенной верно.
   * Если какой-то воркер прислал результат, отличающийся от большинства, сервер помечает его как ненадежный (и при повторении банит).
6. **Сборка (Merger):** Проверенные ответы скармливаются серверному скрипту `merger`, который постепенно собирает итоговую картину анализа.
7. **Финал или отмена:**
   * Когда все подзадачи склеены, статус задачи меняется на `ready`, и клиент забирает красивый отчет (`/get_full_result`).
   * Если клиент передумал и дернул `/cancel_task`, сервер просто выкидывает оставшиеся подзадачи этой задачи из очереди — воркеры мгновенно переключаются на задачи других пользователей.

## 🔌 Клиентский интерфейс (уже спроектирован)

Взаимодействие между веб-редактором и сервером уже описано и реализовано в виде заглушки в `mock.py`. Будущий боевой сервер должен поддерживать этот же контракт:

* `GET /api/v1/get_types` — отдать список доступных алгоритмов анализа.
* `GET /api/v1/get_schema?id=...` — отдать схему настроек для выбранного алгоритма.
* `POST /api/v1/submit_task` — принять задачу в работу и вернуть `taskId`.
* `GET /api/v1/check_task?taskId=...` — сообщить фронтенду, идет ли еще расчет (`active`), упал (`failed`) или готов (`ready`).
* `POST /api/v1/cancel_task` — остановить расчет задачи.
* `GET /api/v1/get_full_result?taskId=...` — отдать готовый HTML-отчет.

## 📡 Протокол взаимодействия воркера (Worker API)

Чтобы любой вычислительный узел мог подключиться к кластеру, он должен общаться с сервером-планировщиком по строгому контракту. Вся логика строится вокруг **состояния сессии**, **таймеров жизни (TTL)** и **управления через Heartbeat**.

### 1. Регистрация в кластере (`POST /worker/register`)
При запуске воркер стучится на сервер и рассказывает о своих возможностях. Сервер оценивает его мощность (чтобы понимать, какие по весу подзадачи ему можно доверять) и выдает учетные данные.

* **Запрос от воркера:**
  ```json
  {
    "arch": "x86_64",
    "os": "linux",
    "cpu_cores": 8,
    "ram_mb": 16384,
    "wasm_runtime": "nodejs-v22-pyodide",
    "numba_supported": true,
    "benchmark_score": 1450
  }
  ```
* **Ответ сервера:**
  ```json
  {
    "workerId": "wrk_9a8b7c6d",
    "sessionToken": "secret_jwt_or_uuid_token",
    "heartbeatIntervalMs": 3000,
    "leaseTimeoutMs": 10000
  }
  ```
  * `heartbeatIntervalMs` — как часто воркер обязан «стучаться» на сервер (например, раз в 3 секунды).
  * `leaseTimeoutMs` — дедлайн (TTL). Если сервер не получит heartbeat в течение этого времени, воркер помечается как **отпавший (dead)**, его `workerId` аннулируется, а текущая подзадача возвращается в очередь для другого узла.

---

### 2. Запрос подзадачи (`POST /worker/pull`)
Когда воркер свободен и готов считать, он запрашивает работу. Воркер может указать свои текущие лимиты (например, сколько свободной оперативной памяти сейчас доступно).

* **Запрос от воркера:**
  ```json
  {
    "workerId": "wrk_9a8b7c6d",
    "availableRamMb": 4096
  }
  ```
* **Ответ сервера (если работа есть):**
  ```json
  {
    "hasTask": true,
    "chunkId": "chk_112233",
    "taskId": "tsk_998877",
    "code": "<base64_encoded_python_algorithm>",
    "codeHash": "sha256:e3b0c44298fc1c149...",
    "payload": {
      "marking":,
      "incidence_matrix": [[-1, 1], [1, -1]],
      "max_steps": 1000
    },
    "maxExecutionMs": 15000
  }
  ```
  * Если задач нет, сервер возвращает `{"hasTask": false, "retryAfterMs": 2000}`.
  * `codeHash` — контрольная сумма, чтобы воркер убедился, что код алгоритма дошел по сети без искажений.
  * `maxExecutionMs` — жесткий лимит времени на расчет этого кванта. Если WASM-песочница не уложится в это время, воркер обязан принудительно убить процесс.

---

### 3. Пульс и канал управления (`POST /worker/heartbeat`)
Это главный механизм живучести и синхронизации. Воркер обязан слать этот запрос каждые `heartbeatIntervalMs` миллисекунд **как в режиме простоя, так и прямо во время тяжелых расчетов в WASM** (для этого сетевой цикл в Node.js работает асинхронно, не блокируясь вычислениями).

* **Запрос от воркера:**
  ```json
  {
    "workerId": "wrk_9a8b7c6d",
    "status": "busy", 
    "currentChunkId": "chk_112233",
    "cpuLoadPercent": 87
  }
  ```
  *(Значения `status`: `"idle"` — простаивает, `"busy"` — считает подзадачу).*

* **Ответ сервера (команды управления):**
  В ответе на heartbeat сервер не просто продлевает жизнь воркеру, но и **управляет его текущими вычислениями**:
  ```json
  {
    "nextDeadlineMs": 10000,
    "command": "continue"
  }
  ```
  Возможные значения поля `command`:
  * `"continue"` — все хорошо, продолжай считать (или ждать работу).
  * `"abort_chunk"` — **стоп-кран!** Пользователь нажал «Отмена» в редакторе, или другие воркеры уже успели посчитать этот кусок и BFT-кворум собран. Воркер обязан мгновенно убить WASM-процесс, очистить память и перейти в статус `idle`.
  * `"re_register"` — сервер перезагрузился или сессия устарела; воркеру нужно заново пройти `/worker/register`.
  * `"ban"` — воркер слишком часто присылал неверные ответы (провалил BFT-проверку), соединение разрывается.

---

### 4. Отправка результата (`POST /worker/submit`)
Как только WASM-контейнер завершил расчет подзадачи, воркер отправляет итог на сервер, уничтожает песочницу в памяти и снова становится свободным.

* **Запрос от воркера (успех):**
  ```json
  {
    "workerId": "wrk_9a8b7c6d",
    "chunkId": "chk_112233",
    "status": "success",
    "executionTimeMs": 420,
    "resultHash": "sha256:8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4",
    "resultData": {
      "deadlock_found": false,
      "reachable_states_count": 512,
      "boundary_markings": [[0, 1, 2, 0]]
    }
  }
  ```
  * `resultHash` — хеш от детерминированного JSON-результата. Позволяет серверу на этапе BFT мгновенно сравнивать ответы от 3–5 разных воркеров без тяжелого парсинга самих данных.

* **Запрос от воркера (если внутри WASM произошел сбой):**
  ```json
  {
    "workerId": "wrk_9a8b7c6d",
    "chunkId": "chk_112233",
    "status": "error",
    "errorType": "OOM_OR_TIMEOUT",
    "errorMessage": "WASM memory limit exceeded during Numba JIT compilation"
  }
  ```
  * Если воркер честно сообщил о технической ошибке (нехватка памяти, таймаут), сервер не снижает ему рейтинг доверия (как за подделку данных), а просто перекидывает этот кусок более мощному воркеру.

## 🛠 Как запустить текущую заглушку (`mock.py`)

Пока боевой кластер находится в стадии идеи, для разработки интерфейса используется локальный mock-сервер:

1. Установить Flask и CORS:
   ```bash
   pip install Flask flask-cors
   ```
2. Запустить сервер:
   ```bash
   python mock.py
   ```
3. Сервер поднимется на `http://127.0.0.1:5000` (базовый путь для API: `/mock`).

## 💡 Практическое замечание по реализации (Гибридный подход: WASM + Docker)

Для максимального охвата участников целесообразно поддерживать **два типа воркеров**, работающих по единому протоколу:

1. **Легкий WASM-воркер в браузере (для массовых пользователей):** Позволяет любому посетителю редактора подключиться к вычислениям в один клик без установки дополнительного ПО. Внутри фонового потока (`Web Worker`) поднимается среда `Pyodide (WASM) + NumPy`, что гарантирует полную безопасность и низкий порог входа.
2. **«Теплый» Docker-воркер с Numba (для выделенных серверов и энтузиастов):** Изолированный контейнер без доступа к сети и диску, где крутится нативный Python с JIT-компиляцией `Numba`. Поскольку один расчет может занимать от 30 секунд и дольше, среда не убивается после каждого кванта — скомпилированные функции кешируются в оперативной памяти по `codeHash` и уничтожаются только при перезапуске или команде `abort_chunk`.

Чтобы не дублировать логику анализа на сервере, используется единый Python-код алгоритма: на мощных узлах декоратор `@njit` компилирует код в машинный через Numba, а в браузерном WASM подменяется на пустую обертку и исполняется поверх NumPy.

**Идея на будущее (Автономный офлайн-режим):** Предусмотреть сборку «всё в одном» (сервер-планировщик + локальный воркер + база алгоритмов в одном пакете или контейнере), чтобы пользователь мог развернуть систему локально и выполнять тяжелый анализ на своем ПК вообще без доступа к интернету всего в пару кликов в браузере предварительной загрузки.
